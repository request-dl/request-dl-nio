- [x] Batch 4: the `@autoclosure`-metadata gotcha from batch 3 (§5, log-level entry) generalizes beyond `Internals.TaskLogger` — it applies to *any* direct `swift-log` `Logger.debug(...)`/`.trace(...)` call using string interpolation, including ones with no relation to `RequestEnvironmentValues.current.logger`. `Tasks/Extensions/Task+Methods.swift`'s `ping(_:logger:)` takes a plain `Logger?` parameter; a `Logger(label:)` built with defaults sits at `.info`, so its `.debug(...)` calls never evaluate their interpolated-string closures. - [x] Batch 4: for a defensive guard reachable only under a specific ordering of async/Combine calls (`PublishedTask.Subscription.request(_:)`'s `guard let subscriber else { return }`, only hit if a subscriber cancels *before* requesting demand — no stock Combine operator does this), a custom minimal `Subscriber` conformance is the fix, not a skip. Both `Subscription.cancel()` and `.request(_:)` are synchronous (guarded by a `Lock`), so driving the exact ordering from a custom subscriber's `receive(subscription:)` needs no `Task.sleep`/timing hacks — assert immediately after the synchronous call returns.
- [x] Batch 5: **an `async` `replace`/similar overload can silently resolve to a *sync* sibling overload at the call site**, even with `try await` written out, if the `perform`/closure argument never actually suspends — a non-async closure literal satisfies an `async throws -> T` parameter type trivially, and Swift's overload resolution prefers the narrower (sync) match. The compiler warns ("no 'async' operations occur within 'await' expression") but still compiles. If a test's whole point is to exercise the *async* overload specifically (`Internals.Override.AssertionFailure.replace`, `Internals.Override.FatalError.replace`), the `perform` closure needs a genuine `await` inside it (e.g. `try? await Task.sleep(nanoseconds: 1)`) to force that resolution — otherwise the coverage gap silently persists despite the test passing and llvm-cov looking "close." Verify with a targeted `swift test --enable-code-coverage --filter <suite>` + `llvm-cov show` on just that file when in doubt, not just "the test passed."
- [x] Batch 5: a metadata/argument dictionary keyed by `type(of: someGenericParam)` (`Internals.Log.unexpectedStateOrPhase(state:phase:error:)`, `cantOpenCertificateFile(_:_:)`) crashes with "Dictionary literal contains duplicate keys" if two same-typed arguments are passed (e.g. two `String`s) — the keys collide. Not a source bug (the generic signature documents that callers pass distinct types), but a real trap for test code reaching for the nearest convenient literal. Use distinct concrete types (custom `enum`/`struct`s) per argument when constructing test data for this shape.
- [x] Batch 5: process-global mutation (`setenv`/`unsetenv` to test `ProcessInfo.processInfo.environment`-reading code, e.g. `FilePath.temporaryDirectory`'s `TMPDIR`/`TEMP`/`TMP` fallbacks) is **not safe** to reach for, even transiently, when other suites read the same environment state and Swift Testing parallelizes across suites by default. Investigate and skip rather than mutate; a `@Suite(.serialized)` trait only serializes within one suite, not against every other suite in the same test binary.
- [x] Batch 5: a live system C API a test cannot substitute a result for (`CFNetworkCopySystemProxySettings()`/`CFNetworkCopyProxiesForURL()` in `Internals.SystemProxyResolver`, or `Internals.Override.Raise`'s real `raise(_:)` signal call) is a legitimate skip category distinct from ordinary fault-injection — the code exists precisely to read live external state or perform a real, process-affecting side effect, and there is no override/DI seam for it (unlike `Internals.Override.AssertionFailure`/`.FatalError`/`.Raise`'s own *replaceable* closures, which very much should be tested — see the `AssertionFailure`/`FatalError`/`Raise` entries in §3 batch 5).
- [x] Batch 5: when a `LocalServer`-style test fixture always waits for a complete request and always answers with a complete response (true of this repo's `LocalServer`), and the code under test needs to react to a connection dying *mid-exchange* at a specific point (mid-upload, head-only, mid-body — see `Internals.ClientResponseReceiver`'s `didReceiveError` state cascade), build a minimal bare `NIOPosix.ServerBootstrap` harness scoped to that one test file instead of extending the shared fixture. A single `ChannelInboundHandler` that reacts to the first bytes read (close immediately / write a head with an unfulfillable `Content-Length` then close / write a head plus a partial body chunk then close) is enough, and keeps the fault-injection surface out of infrastructure every other suite also uses.

- [x] Batch 6: the 85%-line floor and region/function coverage are genuinely different targets — a file can sit at 95%+ line coverage while a single always-taken-the-same-way branch (a `?? fallback`, an `if let` that never fails, a passphrase closure that's constructed but never invoked) keeps region/function coverage well below 85%. "nil"`, `DynamicValueDeepSearch.swift`'s `child.label ?? "_"`) is a legitimate, low-value skip — Swift's `Mirror` gives essentially every ordinary stored property a label, so the fallback exists for a case that's very hard to construct on purpose (and not worth constructing just to touch one line). - [x] Batch 6: `RequestConfiguration.isCacheEnabled` requires a `nil` body — and `MockedTask`'s `content:` block repurposes `Payload` to feed the *mocked response*, not an outgoing request body, through the same `RequestConfiguration.body` field a real request would use. - [x] Batch 6: `DataCache`'s validity check (`Internals.CacheControl.isCachedDataValid`) compares `cachedData.buffer.readableBytes` against the `Content-Length` header on the *cached entry's own* `ResponseHead` — not against the actual byte count of whatever `Data`/file was handed to `CachedData`'s init. When constructing a `CachedData` fixture directly (bypassing a real HTTP round trip), always set `Content-Length` to match the real payload size.
- [x] Batch 6: to force `DataCache`'s memory/disk tiers to decline an entry for size within a single test (not the shared `DataCache.shared`/`testState.dataCache` instance's own capacity setters), pass `memoryCapacity`/`diskCapacity` explicitly through the `.cache(memoryCapacity:diskCapacity:url:)` property builder call itself, not by mutating `dataCache.memoryCapacity`/`.diskCapacity` beforehand. `Internals.CacheConfiguration.build()` floors any *unset or zero* requested capacity back up to a 2 MiB minimum (`CacheConfiguration.minimumCapacity`) via an increase-only merge against the shared `Storage`'s current capacity — so an external override made before the request runs gets silently overwritten back up the moment the property tree resolves, unless the tree itself requests a small positive value.
- [x] Batch 7: `URLEncoder.KeyContainer`/`ValueContainer`'s `unkeyed()` and `URLEncoder.Encoder`'s `getKey()`/`getValue()` look like they'd hit the same `.unset` throw for "nothing was ever encoded," but they check two *different* pieces of state. `unkeyed()` reads the container's own local `key`/`value: String?` (set only by that same container's `encode(_:)`). `getKey()`/`getValue()` read the `Encoder`'s own `_key`/`_value` (set only by `encoder.setKey(_:)`/`setValue(_:)`, which the container's `encode(_:)`/`dropKey()`/`dropValue()` call internally). A custom encoding strategy closure that calls `container.unkeyed()` without ever calling `container.encode(_:)` exercises the container's check but never touches the encoder's — reaching `Encoder.getKey()`/`getValue()`'s own `.none` case needs a closure that does *nothing at all* with its container (no `encode`, no `dropKey`/`dropValue`, not even a read via `unkeyed()`).
- [x] Batch 7: `NIOFileSystem.openFile(forReadingAt:)` opens a directory path without complaint — it does not require the target to be a regular file — and `info(forFileAt:)` (used by `DiskStorage.Record.init?` to check a record's response/data files exist) doesn't distinguish files from directories either. So a fake cache record whose `response.record` is a directory instead of a file passes existence validation and gets an open handle, and only the later `readToEnd` call fails. Useful for deterministically reaching a "we opened it fine but couldn't actually read it" branch without real fault injection — but it lands on the *read* failure, not an *open* failure; forcing `openFile` itself to fail still needs a genuinely unreadable path (permissions), which risks being a no-op under a root CI runner.
